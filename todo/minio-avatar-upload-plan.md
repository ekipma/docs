# MinIO avatar upload integration plan

## Goal

Move user-avatar storage out of the Go container filesystem into S3-compatible object storage backed by MinIO, while keeping avatar URLs stable and avoiding a breaking Flutter release.

The target flow is:

```text
Flutter app -> Go API: request upload
Flutter app -> MinIO: upload to a short-lived presigned URL
Flutter app -> Go API: complete upload
Worker/API -> MinIO: validate, resize, strip metadata, publish variants
CDN -> MinIO: serve processed public avatar
```

## Phase 1: MinIO infrastructure

1. Add MinIO to the deployment environment with a persistent disk, TLS, backups, and monitoring. *(In progress: persistent disk and private compose exposure added; TLS/backups/monitoring remain.)*
2. Keep the MinIO API and console private; expose them only through the internal network or an administration VPN. *(Done for local Compose exposure.)*
3. Create separate buckets or prefixes:
   - `avatar-staging`: private, short-lived uploads.
   - `avatar-public`: processed images served through the CDN.
4. Configure lifecycle cleanup for abandoned staging objects.
5. Create least-privilege credentials:
   - API credentials: create presigned upload URLs and read staging objects.
   - Worker credentials: read staging, write public variants, delete staging.
   - CDN credentials: read-only public bucket access.
6. Add environment variables without committing secrets. *(Done.)*

```env
S3_ENDPOINT=https://minio.internal.example
S3_REGION=us-east-1
S3_BUCKET_AVATAR_STAGING=avatar-staging
S3_BUCKET_AVATAR_PUBLIC=avatar-public
S3_ACCESS_KEY=...
S3_SECRET_KEY=...
S3_PUBLIC_BASE_URL=https://cdn.ekipma.ir/avatars
```

## Phase 2: Image-processing boundary

Create one server-side image pipeline used regardless of whether the bytes arrived through the legacy endpoint or MinIO:

1. Enforce a request/object limit, for example 10 MB for staging uploads. *(Done.)*
2. Verify the object contents, not only its MIME type or filename. *(Done.)*
3. Fully decode the image and enforce pixel dimensions and an allowed format. *(Done.)*
4. Strip EXIF metadata, including GPS data. *(Done for JPEG re-encoding.)*
5. Resize and center-crop into fixed variants, initially `128.webp` and `512.webp`. *(Partially done: JPEG variants currently used.)*
6. Re-encode the output and reject malformed or excessively expensive images. *(Done.)*
7. Write only processed output to `avatar-public`; never publish the original upload. *(Done.)*
8. Delete the staging object after success or after a short retention period after failure. *(Done after success; lifecycle cleanup remains.)*

The published object key should be generated by the server, for example:

```text
avatars/{user-uuid}/{avatar-version}/128.webp
avatars/{user-uuid}/{avatar-version}/512.webp
```

## Phase 3: API contract

Add authenticated endpoints: *(Done.)*

### `POST /api/v1/me/avatar/upload`

The API validates the user and returns an upload ID, object key, and short-lived presigned PUT URL. It must not accept a client-selected user ID or object key.

```json
{
  "uploadId": "...",
  "objectKey": "...",
  "uploadUrl": "...",
  "expiresIn": 300,
  "maxBytes": 10485760
}
```

### `POST /api/v1/me/avatar/complete`

The API verifies that the upload belongs to the authenticated user, processes it, updates the user’s current avatar version/URLs, and returns the processed URLs.

```json
{
  "photoUrl": "https://cdn.ekipma.ir/avatars/{uuid}/{version}/512.webp",
  "thumbnailUrl": "https://cdn.ekipma.ir/avatars/{uuid}/{version}/128.webp"
}
```

Reject completion when the object is missing, expired, too large, the contents are invalid, or processing fails. Make completion idempotent for the same upload ID.

## Phase 4: Database and URL compatibility

Prefer storing an avatar version or object key rather than only a complete URL. *(Done.)* Keep the existing `photoUrl` response field during migration so old app versions continue to work. *(Done.)*

Recommended model fields: *(Done.)*

```text
avatar_object_key
avatar_version
avatar_updated_at
```

Return a versioned URL so cached clients see the replacement immediately. Do not delete the old public object until the new version is successfully published.

## Phase 5: Flutter migration

1. Keep the current `PUT /api/v1/me/avatar` endpoint as a compatibility path. *(Done.)*
2. Add a new REST client method for upload initialization. *(Done.)*
3. Upload directly to the presigned URL with progress reporting and cancellation. *(Done in the REST client; callers can provide progress and a Dio `CancelToken`.)*
4. Call the completion endpoint. *(Done.)*
5. Update the cached avatar URL and invalidate the old cache entry.
6. Preserve the existing fallback avatar behavior for offline/error cases.
7. Release the API compatibility path before shipping the new app.

After adoption, the legacy multipart endpoint can either proxy into the same processing pipeline or be removed in a later breaking API version.

## Security and reliability requirements

- Use HTTPS for the API, MinIO, and CDN.
- Presigned URLs should expire in minutes, not hours.
- Apply per-user and per-IP rate limits to initialization and completion.
- Enforce maximum byte size and pixel count.
- Use separate credentials for API, worker, and CDN access.
- Do not expose MinIO admin credentials to the app.
- Set `Content-Disposition: inline` and an image-only content type for published objects.
- Configure CDN caching for immutable versioned objects.
- Log upload ID, user ID, result, processing duration, and failure reason without logging credentials or presigned URLs.
- Back up MinIO data and test restore procedures.

## Testing and rollout

1. Unit-test image validation, metadata removal, resizing, object-key authorization, and idempotent completion.
2. Integration-test MinIO with a disposable bucket and test credentials.
3. Test oversized files, invalid JPEGs, oversized dimensions, truncated uploads, expired URLs, retries, and concurrent avatar changes.
4. Deploy MinIO and the new API endpoints first.
5. Enable the new Flutter flow behind a server-configurable feature flag or staged app release.
6. Compare upload success rate, processing latency, storage usage, and CDN delivery errors.
7. Migrate existing avatars lazily or with a one-time background job.
8. Remove the old `uploads/` volume only after all production avatars have been verified in MinIO and backups are confirmed.

## Recommended first implementation

For the first iteration, use the Go API as the image-processing worker and MinIO as storage. Add a separate queue/worker only when processing volume justifies it. This keeps the migration small while establishing the correct storage boundary and leaves the API contract ready for asynchronous processing later.
